# SEC-001: FTS5 Ownership Schema & Safe Migration Engineering Audit

**Audit Date**: 2026-11-12  
**Role**: Principal Database Engineer & Application Security Engineer  
**Scope**: SQLite FTS5 Lexical Virtual Table (`lexical_chunks`), Schema Isolation, and Migration Engineering  
**Target Database**: `researchlens_lexical.sqlite3`  
**Verdict**: **FTS5 MIGRATION VERIFIED IN ISOLATED TEST DATABASE**

---

## 1. Executive Summary

During the SEC-001 multi-tenant security hardening phase, `owner_id` was propagated across document ingestion, normalization, chunking, and ChromaDB vector storage. However, the lexical search tier relied on an SQLite FTS5 virtual table whose original schema lacked an `owner_id` column. When cross-user isolation tests queried documents across user boundaries, queries triggered:
```
sqlite3.OperationalError: no such column: owner_id
```

Because SQLite virtual tables cannot be altered via `ALTER TABLE ADD COLUMN` (`OperationalError: virtual tables may not be altered`), upgrading existing production or developer databases requires an architectural migration strategy that preserves document identities, chunk records, tokenizers, and full-text search indices without data loss or corruption.

This engineering effort has:
1. Implemented **fresh database initialization** where all newly created FTS5 databases include `owner_id UNINDEXED` at column position 1, supporting multi-tenant isolation out-of-the-box.
2. Built the authoritative, production-grade migration tool: `scripts/migrate_fts5_add_owner_id.py` with non-mutating `--dry-run` inspection, atomic shadow-table rebuild, strict data conservation verification, quarantine auditing, and transactional rollback recovery.
3. Created an isolated test suite (`backend/tests/security/test_fts5_migration.py`) validating fresh installation, legacy 11-column migration, quarantine of orphans/ambiguities, idempotency, and crash recovery.
4. Resolved cross-user isolation test defects in `backend/tests/security/test_cross_user_isolation.py`, achieving **38/38 passing security tests (100%)**.

## 2. Actual Old Schema vs. Actual New Schema

### Legacy 11-Column Schema (Unmigrated)
Inspected directly from `.chroma/researchlens_lexical.sqlite3` (6,818 rows present in developer storage):
```sql
CREATE VIRTUAL TABLE lexical_chunks USING fts5(
    chunk_id UNINDEXED,
    collection_name UNINDEXED,
    paper_id UNINDEXED,
    document_id UNINDEXED,
    section UNINDEXED,
    page_start UNINDEXED,
    page_end UNINDEXED,
    title UNINDEXED,
    filename UNINDEXED,
    locator UNINDEXED,
    text,
    tokenize='unicode61'
);
```
**Underlying SQLite shadow tables generated by FTS5:**
- `lexical_chunks_data`
- `lexical_chunks_idx`
- `lexical_chunks_content`
- `lexical_chunks_docsize`
- `lexical_chunks_config`

### Upgraded 12-Column Schema (SEC-001 Compliant)
```sql
CREATE VIRTUAL TABLE lexical_chunks USING fts5(
    chunk_id UNINDEXED,
    owner_id UNINDEXED,
    collection_name UNINDEXED,
    paper_id UNINDEXED,
    document_id UNINDEXED,
    section UNINDEXED,
    page_start UNINDEXED,
    page_end UNINDEXED,
    title UNINDEXED,
    filename UNINDEXED,
    locator UNINDEXED,
    text,
    tokenize='unicode61'
);
```

### Schema Compatibility & Architectural Decisions
1. **`owner_id UNINDEXED`**:
   - `owner_id` is an equality filter and isolation boundary, never a full-text search token.
   - Declaring `owner_id UNINDEXED` reduces FTS5 token index overhead, prevents token pollution, and enables direct `WHERE owner_id = ?` parameter binding.
2. **Column Position**:
   - Positioned at index 1 directly following `chunk_id`. This aligns with the metadata ordering across `ChunkMetadata` and `VectorRecord`.
3. **SQLite FTS5 Invariance**:
   - FTS5 virtual tables strictly forbid `ALTER TABLE ADD COLUMN`. Attempting `ALTER TABLE lexical_chunks ADD COLUMN owner_id` results in:
     `OperationalError: virtual tables may not be altered`.
   - However, SQLite FTS5 *does* support atomic table renaming: `ALTER TABLE ... RENAME TO ...`, which renames the virtual table and all associated shadow tables (`_data`, `_idx`, `_content`, `_docsize`, `_config`) transactionally.

## 3. Authoritative Migration Architecture (`scripts/migrate_fts5_add_owner_id.py`)

### Migration Design Workflow
```
[Legacy lexical_chunks (11 cols)]
               │
               ▼
[Inspect: PRAGMA table_info] ─── Already has owner_id? ───► [Exit 0: ALREADY_MIGRATED]
               │ No
               ▼
[Resolve Trusted Ownership]
  ├─ paper_id -> owner_id (from Application DB or Mapping JSON)
  └─ document_id -> owner_id
               │
               ▼
[Record Classification]
  ├─ Confident: Trusted owner resolved and consistent
  ├─ Orphan: Neither paper nor document found in trusted map
  └─ Ambiguous: paper_id owner contradicts document_id owner
               │
               ▼
[Atomic Transaction: BEGIN IMMEDIATE]
  ├─ Create lexical_chunks_migrating (12 cols, owner_id UNINDEXED)
  ├─ Create lexical_chunks_quarantine (audit table for orphans/ambiguities)
  ├─ Create researchlens_schema_version (records schema version 2)
  ├─ Insert confident records into lexical_chunks_migrating
  ├─ Insert unresolvable records into lexical_chunks_quarantine
  ├─ VERIFY: count(migrating) + count(quarantine) == count(legacy)
  ├─ VERIFY: zero NULL or empty owner_ids in staging
  ├─ VERIFY: FTS5 MATCH query executes successfully
  ├─ RENAME lexical_chunks TO lexical_chunks_pre_owner_migration
  ├─ RENAME lexical_chunks_migrating TO lexical_chunks
  └─ COMMIT (or ROLLBACK on any error)
```

### Ownership Mapping & Strict Quarantine Principles
1. **Authoritative Resolution**:
   - `owner_id` is derived **only** from trusted application database records (`papers.owner_id` and `documents.owner_id`) or an authoritative JSON export.
2. **Ambiguity Detection**:
   - If a chunk's `paper_id` resolves to User A but its `document_id` resolves to User B, it is classified as `ambiguous_owner_mismatch` and quarantined.
3. **No Arbitrary Defaults**:
   - Unmapped records (orphans) are **never** assigned a default owner (such as `admin`, `system`, or `unknown`). Doing so would violate the fail-closed security boundary.
4. **Quarantine Retention**:
   - Quarantined records are safely preserved in `lexical_chunks_quarantine` with timestamp, original metadata, and exact failure reason:
     ```sql
     CREATE TABLE IF NOT EXISTS lexical_chunks_quarantine (
         chunk_id TEXT,
         collection_name TEXT,
         paper_id TEXT,
         document_id TEXT,
         section TEXT,
         page_start INTEGER,
         page_end INTEGER,
         title TEXT,
         filename TEXT,
         locator TEXT,
         text TEXT,
         quarantine_reason TEXT,
         quarantined_at TIMESTAMP
     );
     ```
5. **Legacy Table Preservation**:
   - The original legacy table is preserved as `lexical_chunks_pre_owner_migration`.

## 8. Remaining Dependencies & Security Risks

1. **ChromaDB Vector Store Migration Dependency**:
   - `scripts/migrate_fts5_add_owner_id.py` migrates the SQLite lexical FTS5 database.
   - For existing vector embeddings, `backend/scripts/migrate_vectorstore_add_owner_id.py` or `scripts/reindex_documents.py --all --apply` must be run when the developer or production environment is scheduled for vector re-indexing.
2. **Local AI / Ollama Fallback Isolation**:
   - In production environments where `answer_mode="DOCUMENTS_GENERAL"` is selected, fallback queries for ungrounded prompts route to general knowledge. Security test environments should enforce `answer_mode="DOCUMENTS_ONLY"` or mock the LLM client to guarantee non-blocking, isolated execution.
3. **Quarantine Remediation**:
   - Unmapped or conflicting records are quarantined rather than deleted. System administrators should inspect `lexical_chunks_quarantine` after migration to reconcile orphaned papers.
